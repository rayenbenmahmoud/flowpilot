# Demo mode and limitations

## What demo mode does

`FLOWPILOT_DEMO_MODE=true` (the default):

- **Email** is never sent. The email adapter writes the message to the Outbox (shown as *Simulated*).
- **n8n** and **partner API** calls make no network request; the adapter returns a simulated acceptance.
- Integration screens say *Simulated (demo mode)*; "connected" can never be shown. The test button runs a clearly labelled simulated check.
- Guided-demo tools and the reset button are available (they return `403 demo_disabled` otherwise).
- A banner at the top of every screen states the mode.

Deterministic simulated failures (so reviewers can see error handling):

| Trigger | Simulated result |
|---|---|
| Recipient `…@bounce.example.com` | Permanent failure `recipient_rejected` (not retryable) |
| Recipient `…@flaky.example.com` | `smtp_timeout` on attempt 1 only (retry succeeds) |
| n8n path `simulate-outage` | `connection_error` (retryable) |
| Integration turned off in the UI | `integration_disabled` with a fix hint |

The seeded history (about 70 executions over 7 days) is **synthetic data generated by `seed_demo`**, with a fixed random seed. It is not real traffic.

## Going live

1. Set `FLOWPILOT_DEMO_MODE=false`, a real `DJANGO_SECRET_KEY`, `DJANGO_DEBUG=false`.
2. Provide credentials for the integrations you want (see `.env.example`).
3. Open **Integrations** and press **Test connection**. Only a passing live test shows *Connected*. Until then the status reads *Not configured* or *Configured, not tested*.

**Live mode has been tested only against mocked HTTP and Django's in-memory mail backend**, not against real SMTP, n8n or partner services. Treat live integrations as unverified until you test them with your own credentials.

## Known limitations

- Single-tenant, one active session per user, no roles beyond "authenticated". Not a multi-user product.
- Dashboard tokens do not expire (they are replaced on each login and deleted on sign-out). Stored in `sessionStorage`, so an XSS bug would expose them; a production build should prefer an HTTP-only cookie session.
- Executions stuck in `Running` after a worker crash are not auto-recovered.
- Rate limiting is per client IP using the Django cache (Redis in Compose, process-local without it). Behind a proxy set `FLOWPILOT_NUM_PROXIES`.
- Conditions use simple comparisons; there is no branching, looping or scheduling.
- The email adapter uses Django's `EMAIL_*` settings, which Django 6.1 has deprecated in favour of `MAILERS` (removal is planned for Django 2028); migrating is a small follow-up.
- Dates in filters are UTC.
- No performance or load testing was done; no throughput figures are claimed.
